# ЛР № 10. Тестирование «Сириус.Еды»

В работе проверяются создание заказа в PostgreSQL, поведение сервиса под нагрузкой и запуск тестов при изменении кода. Бонусы включают контракт между монолитом и кухней и мутационное тестирование расчёта суммы заказа.

## 1. Интеграционные тесты и покрытие

Нужны Python 3.12, запущенный Docker и Redis для существующих тестов API. Активируйте виртуальное окружение проекта и установите зависимости. Для окружения, созданного через `uv`, можно установить их командой `uv pip install -r requirements-test.txt`.

```bash
python -m pip install -r requirements-test.txt
docker compose --env-file .env.example up -d redis
pytest tests --ignore=tests/integration --ignore=tests/contract -v
pytest tests/integration -v
pytest tests/contract -v
pytest --cov=app --cov-report=html
```

[Testcontainers](../../tests/integration/conftest.py) поднимает временную PostgreSQL 15 с pgvector и случайным локальным портом. Alembic применяет все миграции к URL контейнера. FastAPI использует его в зависимости `get_db`. Фоновые задачи Celery подменены, поэтому интеграционные тесты можно запускать отдельно, имея только Docker. После каждого теста очищаются изменяемые таблицы с зависимыми строками. Справочники, заполненные миграциями, сохраняются до конца сессии.

[Тест заказа](../../tests/integration/test_orders.py) проходит по цепочке JWT → FastAPI → сервис → SQLAlchemy → PostgreSQL. В текущем API успешное создание возвращает HTTP 200, а ID студента берётся из JWT. Тест загружает закоммиченную строку в другой сессии и проверяет владельца, блюдо, количество, статус, сумму и ID запроса. Для 401 и 400 он проверяет отсутствие записей. Полный локальный прогон дал 75 успешных тестов и 73% покрытия строк `app`. HTML-отчёт открывается из `htmlcov/index.html`.

## 2. Нагрузочный тест

Запускать на учебной базе. Сценарий добавляет заказы, а Celery ставит имитации генерации PDF и отправки email в очередь Redis. Скопируйте `.env.example` в `.env` для нового стенда и задайте `SECRET_KEY`.

```bash
docker compose up -d --build api kitchen celery-worker redis-exporter prometheus grafana
curl -f http://127.0.0.1:8000/menu/items

# Из каталога проекта, с активным виртуальным окружением.
# Seed использует тот же SECRET_KEY и PostgreSQL, что запущенный API.
seed_env=$(mktemp)
python -m loadtest.lab10.seed > "$seed_env"
set -a
source "$seed_env"
set +a
rm "$seed_env"

locust -f locustfile.py --host http://127.0.0.1:8000 --web-host 127.0.0.1
```

В [Locust](http://127.0.0.1:8089/) задайте 50, затем 100 и 200 пользователей, со скоростью запуска 10 пользователей/с. Для записи сопоставимых CSV выполните три запуска. JWT от синтетического пользователя действует 15 минут. При истечении выпустите новый командой подготовки данных.

```bash
for users in 50 100 200; do
  locust -f locustfile.py --host http://127.0.0.1:8000 --headless \
    -u "$users" -r 10 -t 65s --reset-stats --csv "/tmp/sirius-lab10-$users"
done
```

`LOCUST_ORDER_TOKEN` включает сценарий с заказами. Без него запускается прежний сценарий чтения меню из ЛР № 4. Вес запросов в [сценарии](../../locustfile.py) равен 7 для списка блюд, 2 для карточки и 1 для создания заказа. После каждого запроса пользователь ждёт от 1 до 3 секунд. `--reset-stats` сбрасывает статистику после завершения разгона. В [Grafana](http://127.0.0.1:3000/d/sirius-food-lab10/) сравните HTTP RPS, p95 и 5xx с длиной очереди `default` и загрузкой процесса API. Длину очереди можно независимо сверить командой `docker compose exec redis redis-cli LLEN default`.

### Результаты 24 ноября 2026

Три последовательных прогона на одной локальной сборке, по 65 секунд каждый. Locust измерял HTTP после разгона. Длину очереди сняли в Redis перед каждым прогоном и сразу после него. [Данные по маршрутам](locust.csv).

| Пользователи | Запросы | Средний RPS | p95 всех, мс | p95 заказа, мс | Ошибки HTTP | Очередь Celery |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 50 | 1516 | 25,02 | 17 | 23 | 0 | 0 → 257 |
| 100 | 2809 | 50,47 | 17 | 24 | 0 | 257 → 740 |
| 200 | 4465 | 99,15 | 19 | 30 | 0 | 740 → 1720 |

На этом стенде p95 остался ниже 1 с, а ошибок 5xx до 200 пользователей не было. Верхнее измеренное значение загрузки API по 20-секундному окну составило около 36% одного ядра.

**Узкое место — воркер Celery.** В очереди `default` накопилось 1720 задач. При 200 пользователях Locust измерил 9,40 создания заказа в секунду. Каждый такой запрос ставит генерацию PDF и отправку email в Redis. Настройки стенда задают два процесса Celery, а код задач имитирует 2 с работы для PDF и 1 с для email. Поэтому задачи поступают быстрее, чем два процесса заканчивают их. HTTP отвечает после постановки задач, поэтому его p95 остаётся низким, пока растёт очередь фоновой обработки.

## 4. Бонус Pact

```bash
pytest tests/contract -v -s
```

[Тест](../../tests/contract/test_order_paid.py) создаёт `Kitchen-SiriusFood.json` во временном каталоге pytest. Пример асинхронного сообщения проходит через `process_message` consumer кухни. Затем Pact проверяет тело, построенное функцией монолита `order_paid`. Рабочий контракт `order.paid` содержит `event_id`, `order_id`, `customer_id` и `amount`. Переименование `amount` в `total` в контрольном сообщении приводит к ошибке Pact `missing the following keys: amount`.

## 5. Бонус mutmut

```bash
mutmut run --no-progress
mutmut results
mutmut show 6
mutmut show 7
```

[Конфигурация](../../setup.cfg) ограничивает анализ функцией расчёта суммы в `app/modules/orders/amounts.py`. Команда запускает класс `OrderServiceTest`, включая три добавленных теста, и проверяет мутации по одной.

| Прогон | Всего | Убито | Выжило |
| --- | ---: | ---: | ---: |
| До усиления тестов | 18 | 8 | 10 |
| После усиления тестов | 18 | 16 | 2 |

Проверки фиксируют умножение цены на количество, округление половины копейки вверх, допустимые границы и отклонение неконечных значений. Выжившие мутации № 6 и № 7 включают ноль или верхнюю границу в первую проверку. Обе суммы всё равно отклоняются второй проверкой после округления с тем же исключением. Код возврата mutmut `2` означает, что остались выжившие мутации.

## 6. Контрольные вопросы

1. **Чем unit-тест отличается от интеграционного?** Unit-тест проверяет отдельное правило в изоляции. Интеграционный тест проверяет, как совместно работают HTTP-слой, сервис, репозиторий и PostgreSQL.
2. **Зачем Testcontainers?** Каждый прогон использует отдельную БД нужной версии. Миграции создают реальную схему, тесты добавляют собственные данные.
3. **Зачем пирамида тестов?** Большую часть поведения проверяют быстрые unit-тесты. Меньшее число интеграционных и E2E-тестов проверяет взаимодействия и ключевые пользовательские сценарии.
4. **Что проверяет нагрузочный тест?** Пропускную способность, задержки и ошибки при одновременной работе пользователей.
5. **Почему нужны метрики?** Locust показывает симптомы снаружи. Метрики API и очередей помогают определить, какой компонент ограничивает обработку.
6. **Зачем контрактный тест?** Он проверяет, что отправитель формирует сообщение, которое получатель понимает, включая обязательные поля и их типы.
7. **Что значит, что мутация выжила?** После контролируемого изменения кода тесты остались зелёными. Изменение могло оказаться ненаблюдаемым, либо тестам не хватало проверок.
8. **Почему покрытия 90% мало?** Покрытие показывает, какие строки выполнялись. Корректность зависит от проверяемых условий, граничных случаев и утверждений о результате.
9. **Зачем CI?** Он повторяет проверку на каждом изменении кода. Если обязательная проверка красная, GitHub блокирует слияние PR в защищённую ветку.
10. **Почему важна изоляция тестов?** Результат должен зависеть от входных данных данного теста и проверяемого кода, независимо от порядка запуска.

На защите покажите зелёный прогон интеграционных тестов, статистику Locust, график очереди в Grafana, оба состояния CI и результаты Pact и mutmut.
